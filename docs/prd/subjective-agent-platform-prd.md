# 主观评测 Agent Workbench PRD

**状态：DRAFT，等待产品范围和技术选型确认**
**目标分支：`develop`**
**产品目标：面向复杂数学问题，建设支持证据校验、长任务恢复与研究复核的数学推理工作台**
**当前研发重心：工程完成度、产品体验和主观评审展示；官方评分链路继续独立运行**

## 1. 评分约束是产品需求的上位目标

比赛总分为 100 分：

| 评分项 | 权重 | 评委重点 |
| --- | ---: | --- |
| 客观评测：答案正确性 | 60 | 统一评测集正确率；接口或 JSON 格式错误视为未通过 |
| 主观评测：推理策略与系统设计 | 10 | 架构完整性、任务拆解、推理规划、过程校验、模块协同、可解释性 |
| 主观评测：展示质量 | 20 | Demo 稳定性、交互完整性、视频、技术报告、结果规范、复现便利性 |
| 主观评测：创新性与可扩展性 | 10 | 机制创新、协作方式、验证机制、场景迁移、持续扩展潜力 |

主观档位：系统设计 A 8–10、B 5–7、C 0–4；展示质量 A 16–20、B 10–15、C 0–9；创新与扩展 A 8–10、B 5–7、C 0–4。

同分时先比较答案正确性，再比较系统设计，最后比较创新性。结构化 JSON、必要日志和可复核结果属于底线要求。

**产品推论：** 用一条完整数学任务串起工程能力，让评委看到每个机制针对什么求解困难、如何工作、产生什么证据。研发优先级由主观评审的系统设计、展示质量与创新扩展决定；新增能力在独立 Workbench 中运行。

## 2. 产品定位

> 数学推理工作台围绕复杂数学问题的可靠求解，组织问题条件、求解计划、专业子智能体、外部资料与计算工具，保存可恢复的推导状态，并交付可检查、可解释、可复核的解答。

用户使用它的理由：

1. 将长题、多条件和多小問组织为可检查的求解任务；
2. 对定理前提、候选冲突和计算结果提供可追溯的检查依据；
3. 在中断后恢复已保存的阶段成果，回看不同解法与验证过程；
4. 将解答、资料引用和验证记录组织成可用于学习、讨论和研究复核的成果。

### 2.1 对外叙事：从数学困难讲工程机制

介绍顺序统一为：**数学困难 → 设计目标 → 工程机制 → 可观察的运行证据**。页面、视频与报告优先呈现题目、条件、子任务、解答、验证与来源；框架名和技术细节放在架构视图中展开。

| 工程亮点 | 面向数学任务的表达 | 评委能看到什么 |
| --- | --- | --- |
| 持久化与 checkpoint | 长程求解的阶段保存和中断恢复 | 已完成的子任务和检查结果在重启后仍可读取 |
| 子智能体与图式编排 | 求解、条件检查、反例审查的职责分工 | 子任务委派、输入范围、结论与汇总过程 |
| 联网搜索 | 定理、定义和方法依据的来源检索 | 来源卡片、引用位置与适用前提检查 |
| 数学工具、工具注册与后续 MCP | 为计算和检验选择可追踪的工具 | 参数、工具版本、结果及与当前结论的关系 |
| 后续计算沙箱 | 为程序辅助数学探索提供隔离、可复现的环境 | 代码、环境、数值实验和生成图表 |
| 后续长期记忆 | 管理带来源和适用条件的方法笔记 | 笔记检索、版本和本题使用理由 |
| 事件流与观测面板 | 定位推导中断、证据缺口和校验分歧 | 当前步骤、工具失败、未完成义务和成本 |
| 人工复核 | 研究场景中的条件澄清与下一步选择 | 审阅意见和恢复记录；官方自动评测不开放此入口 |
| 回放与运行比较 | 复核解题路径及改动前后的依据 | 原记录回看、不同运行的差异与来源 |
| 解释与证据导出 | 交付可检查的数学解答和学习材料 | 结论、关键论证、适用条件、引用、工具检查 |
| 后续反思与 RSI 实验 | 将失败复盘转为可审查的方法改进候选 | 版本差异与独立验证记录，未经验证的建议保持候选状态 |

这些是产品设计目的与待实现能力，不是已取得的正确率结果。功能广度可以体现在主观展示中，新增功能进入产品 MVP 的验收以机制真实运行和交互完整为主，不要求每个模块先证明官方正确率提升。

### 2.2 成效表述

- **设计目的**：使用“旨在减少条件遗漏”“支持推导复核”“为正确求解提供依据”。
- **工程效果**：用真实运行记录说明“恢复了哪一阶段”“发现了哪个冲突”“引用了什么来源”。
- **数学收益**：只有对应评测支持时才使用“提高正确率”“减少数学错误”等实测表述。
- 持久化、观测、界面与导出主要支持连续性、诊断和复核；子智能体、检索与工具也可能引入新错误，不能直接据功能存在推导正确率增长。
- 报告同时标明运行模式和功能状态；产品演示的贡献与官方成绩分别说明。

## 3. 目标用户与场景

### 3.1 评委演示者

需要在 5 分钟内证明架构完整、Demo 稳定、创新机制可解释。

### 3.2 数学学习者/研究者

输入复杂数学问题，查看计划、依据、验证结果和解释，必要时批准下一步。

### 3.3 Agent 工程师

配置角色、工具、执行图和预算，查看运行事件，回放失败，并比较不同工作流。

### 3.4 三个固定演示场景

1. **多条件问题的协作求解**：提取条件和目标 → 规划子任务 → 求解与独立检查 → 展示一致或有分歧的依据 → 解答与证据导出。
2. **有来源的数学研究**：检索定理与定义 → 检查适用前提 → 计算或验证 → 在报告中关联结论和来源。联网故障须明确呈现，不能用预置答案代替实时研究。
3. **长任务恢复与研究复核**：显式注入工具超时 → 保存阶段状态 → 重启后读取 checkpoint → 用户选择重试或接受部分结果 → 导出恢复记录。恢复粒度为已持久化阶段，不承诺接续未保存的模型内部推理。

## 4. 产品边界

### 4.1 本项目负责

- 会话、运行和产物管理；
- 图式 Agent 编排；
- 多角色协作；
- 搜索和工具适配；
- 持久化、回放、事件流和复核；
- Demo、报告和主观评分证据。

### 4.2 本项目暂不负责

- 默认官方评分链路的模型策略重写；
- 训练基础模型；
- 为某个题号制作答案特判；
- 同时引入多套 Agent 框架作为运行时依赖；
- 以结构测试或 Demo 成功冒充数学能力提升。

## 5. MVP 定义

MVP 必须能在单机上完成一次真实、可观察、可回放的运行，并覆盖三项主观评分。

### 5.1 MVP 功能

1. **Workbench 页面**：新建会话、输入问题、查看运行列表和运行详情。
2. **图式编排**：使用一个成熟的图式编排框架；首选 LangGraph 的图、checkpoint 和 interrupt 模式。
3. **五个角色**：Intake 整理条件和目标，Planner 规划子任务，Solver 通过 Adapter 调用当前官方 Agent，Verifier 记录检查依据和分歧，Synthesizer 组织解答与证据。单独展示哪些角色产生了模型调用，哪些属于确定性处理，不能把静态步骤标签计作真实子智能体执行。
4. **持久化**：SQLite 保存会话、运行、阶段、事件、checkpoint、工具调用和产物索引。
5. **状态流**：`received → planned → solving → verifying → synthesizing → completed/failed/needs_review`。
6. **真实联网搜索 Adapter**：接入一个可配置的搜索供应商；保存来源、摘要、时间和链接；无凭证时使用明确标记的 replay 数据。
7. **工具注册中心**：至少注册搜索工具和一个数学验证/计算工具，统一记录参数摘要、状态和耗时。
8. **事件流**：使用 SSE 向页面推送阶段、角色、工具、错误和完成事件。
9. **人工复核**：在角色冲突、来源不足或工具失败时暂停，允许批准、重试或改路线。
10. **回放和导出**：按 Run ID 回放阶段时间线，导出 JSON 和 Markdown 证据包。
11. **官方隔离**：产品入口不被根 `user_agent.py` 导入，全部新功能默认不进入官方评测。

### 5.2 MVP 明确不做

- 多框架并存；
- 分布式队列和多机执行；
- 向量数据库长期记忆；
- Docker 代码沙箱；
- 自我训练、RSI、自我修改；
- 完整插件市场；
- 任何以提高官方正确率为目标的 Prompt 调优。

### 5.3 MVP 验收

- 现场 5 分钟内完成一次数学解题演示；
- 现场 5 分钟内完成一次搜索/工具/报告演示；
- 可人为触发工具失败并恢复；
- 关闭模型凭证时，系统显示明确配置错误，不无限等待；
- 浏览器刷新后仍能查看已完成运行；
- 任一运行可以导出并在干净环境中回放；
- 官方 `user_agent.py` 的导入、默认请求预算和返回结构不变。

## 6. MVP 之后的扩展优先级

### P1：展示完整度

- 多 Solver 并行和候选比较；
- 运行差异比较；
- 论文资料库与长期记忆；
- OpenTelemetry 导出；
- OpenHands 风格的受控沙箱 Adapter；
- CrewAI 风格的 Flow/Memory 组件。

### P2：研究性创新

- Debate/Reflection 工作流；
- 自动生成执行图；
- 复杂任务的子图与子 Agent；
- 运行策略自动选择；
- RSI 或持续改进机制的隔离实验。

P2 功能只进入产品 Demo 或实验 Profile，不自动进入官方 Profile。

## 7. 主观评分证据矩阵

| 评分项 | 产品证据 | MVP 验收证据 |
| --- | --- | --- |
| 系统设计 10 | 架构图、角色接口、状态图、checkpoint、预算和失败回退 | 一次完整运行的阶段事件与角色协作记录 |
| 展示质量 20 | Workbench、稳定 Demo、SSE 状态、回放、导出、技术报告 | 5 分钟演示脚本、录屏、JSON/Markdown 结果包 |
| 创新扩展 10 | 图式编排、多角色协作、联网研究、工具注册、人工复核、插件 Adapter | 三个演示场景和一个故障恢复场景 |

## 8. 关键非功能要求

- 所有运行都有唯一 Run ID；
- 所有状态变化都产生结构化事件；
- Trace 不含 API key、完整 prompt、个人信息或隐藏答案；
- 工具拥有显式权限、超时和调用预算；
- 运行可以暂停、恢复、重试和回放；
- 产品功能与官方评分功能分开安装、分开配置、分开验收；
- 运行结果可 JSON 序列化；
- 页面加载失败时显示可操作错误，不显示空白页。

## 9. 决策记录

PRD 确认前不写产品侧代码。下一轮需要确认：

1. MVP 是否选 LangGraph 作为主编排框架；
2. 搜索供应商和凭证注入方式；
3. 前端采用 React/Vite 还是轻量服务端页面；
4. 是否把 OpenHands 沙箱放入 P1；
5. 现场演示是否使用真实联网，还是同时准备可标注的 replay 模式。
